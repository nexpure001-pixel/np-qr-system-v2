# スタッフ端末管理の導入

## 使い方

1. 管理者が `/admin/staff` で対象イベントを「受付開始」にする。
2. 必要なら「おすすめにする」を選ぶ。端末の選択は自動では変わらない。
3. 端末名（例：正面受付・田中さん）を入力し、招待QRを発行する。
4. スタッフが自分のスマホでQRを読み、「この端末を登録して受付へ」を押す。
5. スタッフが対象イベントを選択して確定し、カメラを開始する。
6. 別イベントへは画面上部の「イベントを切り替え」から変更する。
7. 管理者は受付終了・端末無効化・未使用の招待の無効化を行える。

招待は24時間・1回限り、端末登録は7日間。期限は自動延長しない。
招待QRは受付権限を付与するため、担当スタッフにのみ共有する。
URLは発行元サイトと同じドメインになる。本番管理画面から発行すること。
ログアウトするとその端末登録も無効化され、再利用には新しい招待が必要。
従来の企業コード・イベントコード・パスコードによるログインも残るが、
この場合の端末はその1イベントだけ利用できる。複数イベントの切替には管理者の招待を利用する。

## 本番反映の順序

1. 本番DBのバックアップと既存スキーマを確認。
2. `supabase/migration_v8_staff_devices.sql` を既存Supabaseに適用。
   追加テーブル・関数だけを作成し、既存イベントや参加者を削除しない。
   対応する既存列は `participations.company_code/name/ticket_type/start_time/re_entry_history(jsonb)`。
3. 本番サーバーの `NEXT_PUBLIC_SUPABASE_URL`、`NEXT_PUBLIC_SUPABASE_ANON_KEY`、
   `SUPABASE_SERVICE_ROLE_KEY` を確認。service roleキーはサーバー専用。
4. 管理者が `/admin/staff` を使える版をデプロイし、対象イベントを受付開始にする。
   新テーブルの初期状態ではイベントは受付停止。イベント未定なら開始しない。
5. 招待QRで端末を登録し、実機で受付を確認。

この変更で旧形式のスタッフCookieは利用しなくなる。初回だけ端末を登録し直す。
既存の本番にはまだSQL適用・デプロイしていない。

## 検証

`npm run test:staff`（PGlite上で実際のmigration/RPCを実行）、`npm run lint`、`npm run build`。
テストは招待再利用・期限切れ・無効化、企業境界、単一イベント権限、
受付終了、古い画面からの受付、推薦変更、初入場・再入場、曖昧なID、APIロール権限を確認する。
PGliteは単一接続のため、本番PostgreSQLの複数接続による競合試験の代替ではない。

画面上のイベント一覧は表示中のみ30秒ごとと画面復帰時に更新する。
受付ごとにDB内で登録端末・有効期限・対象イベント・受付状態を再確認する。
端末行と受付設定行をロックして処理し、受付と切替/無効化/終了の競合を直列化する。
処理が既に確定した受付は、後から端末を無効化しても取り消さない。

実機で必要な確認：iPhone Safari / Android Chromeで招待登録、ブラウザー再起動後の復帰、
イベント切替、受付終了/端末無効化後の拒否、カメラの開始/休止、連続受付時の発熱。
表示確認はモックデータ、SQLの検証はローカルDBで行い、実参加者の入場記録は変更しない。

既存スキーマのpublicアクセス方針はこの移行では変更しない。
スタッフ用の新テーブルとRPCはanon/authenticatedの直接アクセスを拒否し、
管理操作では認証ユーザーの所有企業をサーバーで検証する。
